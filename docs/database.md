# Database

Postgres 17 (docker compose) accessed through **TypeORM 1.x** from the api
and the worker.

## Local database

- `docker-compose.yml` defines a `postgres` service (plus `rabbitmq` and
  `mailpit`; see [Messaging](messaging.md)). It reads `DB_USER`,
  `DB_PASSWORD`, `DB_NAME`, and `DB_PORT` from `.env`, and has a `pg_isready`
  healthcheck (`docker compose up -d --wait` returns once it's ready).
- Data lives in the `postgres-data` volume. `docker compose down -v` deletes
  it.
- Two databases on that server:
  - `vulnscan`: development, used by `script/server`
  - `vulnscan_test`: integration tests, created by `apps/api/test/global-setup.ts`
    (or the worker's, whichever runs first)
- Connect: `docker compose exec postgres psql -U app -d app`.

## DataSource

`@repo/entities` exports what every process needs
(`packages/entities/src/data-source.ts`):

- `postgresOptions(config)`: TypeORM options with every entity registered
  and `synchronize: false`,
- `synchronizeSchema(dataSource)`: creates every Postgres **schema** the
  entities use (`CREATE SCHEMA IF NOT EXISTS`; TypeORM's `synchronize`
  doesn't do this), then runs `synchronize()` to create and alter tables,
  holding a Postgres advisory lock so concurrent processes (the api, test
  setups) don't alter the schema at the same time.

`apps/api/src/database.ts` builds the options from `@repo/config/api`;
`AppModule` imports them with `TypeOrmModule.forRootAsync(databaseOptions)`,
and when `NODE_ENV !== "production"` it runs `synchronizeSchema` on startup.

`apps/worker/src/database.ts` builds the same options from
`@repo/config/worker` but **never synchronizes or creates schemas**: the api
owns the schema, and a second process altering tables could race it or, on
an older branch, undo its changes. The worker therefore needs the api to have
run once after an entity change. Its integration tests sync the test database
in their global setup instead.

In production neither process changes the schema. **There are no migrations yet.** Before the
first production deploy, add TypeORM migrations; the first one must create the
`auth` schema. Then update this page.

## Entities

Entities live in `packages/entities/src/` and are exported from
`src/index.ts`; the `entities` array that `postgresOptions()` registers is in
`src/entities.ts`.

Conventions:

- File name `<name>.entity.ts`, class name in PascalCase.
- Property names camelCase; **column names snake_case** via
  `@Column({ name: "created_at" })`.
- Text primary keys (`@PrimaryColumn({ type: "text" })`) for Better Auth
  tables, because Better Auth generates the IDs.
- `timestamptz` for timestamps.
- Foreign keys: a plain `userId` column plus a `@ManyToOne` relation with
  `@JoinColumn({ name: "user_id" })` on the same column, and
  `onDelete: "CASCADE"` where the child shouldn't outlive the parent.

The package is compiled (`tsc` → `dist/`) because the api imports it at
runtime; see [Architecture](architecture.md#workspaces).

## Schemas

| Schema   | Contents                                                                             | Owner       |
| -------- | ------------------------------------------------------------------------------------ | ----------- |
| `auth`   | `user`, `session`, `account`, `verification`, `organization`, `member`, `invitation` | Better Auth |
| `public` | `email_delivery`, `project`                                                          | app code    |

Put an entity in a schema with `@Entity({ schema: "auth", name: "user" })`.
`user` is a reserved word in Postgres, so hand-written SQL must quote it:
`auth."user"`.

## App tables

| Entity          | Table            | Holds                                                                                                                                                                                       |
| --------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `EmailDelivery` | `email_delivery` | one row per email message the worker sends, keyed by the queue message id (`message_id`); `type`, `recipient`, `status` (`sending`/`sent`), `claimed_at`, `sent_at` → `auth.user` (cascade) |
| `Project`       | `project`        | one app a user deploys: `name`, `name_key` (`lower(name)`, generated), `created_at`, `updated_at` → `auth.organization` (cascade); unique on (`organization_id`, `name_key`)                |

App tables use `uuid` primary keys generated by Postgres
(`@PrimaryGeneratedColumn("uuid")`), except `email_delivery`, keyed by the
queue message's id, which is what makes sending idempotent (see
[Messaging](messaging.md#idempotency)). App data belongs to an
organization (`organization_id` → `auth.organization`), not to a user. A
name unique ignoring case gets a generated `lower(name)` column and a
unique constraint on it, since TypeORM can't synchronize an index on an
expression (see
[Decisions](decisions/case-insensitive-unique-names-through-a-generated-column.md)).
A calendar date with no time is a
`date` column whose entity property is a `YYYY-MM-DD` string.

## Fixtures (sample data)

`script/seed` loads `@repo/fixtures` into the development database
(`DB_NAME`): so far 5 verified users, each with the personal organization
sign-up gives every user (see [Authentication](auth.md#organizations)),
and 4 projects in Alice's and Ben's. The data is plain TypeScript in
`packages/fixtures/src/data/`; records refer to each other by natural keys
(e.g. a user's email), typed with `as const` so the keys are type-checked.
Every fixture user's password is `fixturePassword` in `data/users.ts`. The
integration tests take sample values from it too, without seeding it (see
[Testing](testing.md#writing-integration-tests)).

The seeder (`apps/api/src/fixtures/seed-fixtures.ts`, run by
`apps/api/src/seed.ts`) signs users up through Better Auth and marks them
verified through its internal adapter; app tables (projects) are written
with TypeORM. It's idempotent: existing users and projects are skipped. It refuses to run
when `NODE_ENV=production`, since the fixture password is public. To start
over, `docker compose down -v` and run `script/server` (or `script/seed`)
again.

## Better Auth tables

| Entity           | Table               | Holds                                                                                               |
| ---------------- | ------------------- | --------------------------------------------------------------------------------------------------- |
| `BaUser`         | `auth.user`         | name, email (unique), email_verified, image                                                         |
| `BaSession`      | `auth.session`      | token (unique), expiry, IP, user agent, `active_organization_id` → user (cascade)                   |
| `BaAccount`      | `auth.account`      | one row per sign-in method; the email/password hash (`provider_id = 'credential'`) → user (cascade) |
| `BaVerification` | `auth.verification` | verification tokens (e.g. email verification)                                                       |
| `BaOrganization` | `auth.organization` | organizations (organization plugin): name, slug (unique), logo, metadata; one personal one per user |
| `BaMember`       | `auth.member`       | a user's membership of an organization and their `role` → organization, user (both cascade)         |
| `BaInvitation`   | `auth.invitation`   | invitations to an organization (unused until teams) → organization, inviter (both cascade)          |

**Never write to these tables directly**: no repository writes, query-builder
writes, or raw SQL. Change them through Better Auth only. Reading is fine, as
is a foreign key from an app table to `auth.user`. The only exception is test
fixture setup and teardown. See [Authentication](auth.md#rules).

Entity property names must match Better Auth's field names exactly, because
the adapter passes them through. Check Better Auth's schema before renaming a
property or adding a plugin that adds fields.
