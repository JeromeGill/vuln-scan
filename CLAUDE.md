# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

pnpm + Turborepo monorepo. Workspaces are `apps/*` and `packages/*`.

- `apps/web` — Next.js 16 (App Router, React 19) app, dev server on port 3000: shadcn/ui (Tailwind v4), TanStack Table v9 / Form / Query, oRPC client; an installable PWA (manifest, generated icons, service worker); see `docs/web.md`
- `apps/api` — NestJS 12 server (Express), listens on `PORT` (default 3002); TypeORM + Postgres, Better Auth (email verification required, optional Google sign-in); oRPC routes from `@repo/contracts`; publishes jobs to RabbitMQ
- `apps/worker` — NestJS 12 application context (no HTTP server) consuming RabbitMQ job queues with `amqplib`; sends email (nodemailer SMTP, Mailpit locally); see `docs/messaging.md`
- `apps/e2e` — Playwright browser tests: starts the api (3102), worker, and web (3100, `next dev`; `E2E_MODE=prod` for a production build) itself against its own `app_e2e_test` database and vhost, runs every route and each UI story's main flow on desktop Chromium and a Pixel 7 viewport, and fails any test whose page logs a console error or warning (exceptions in `console-allowlist.ts`, each with a reason); see `docs/testing.md#browser-tests`
- `packages/entities` (`@repo/entities`) — TypeORM entities shared by the api and worker: Better Auth's (`auth` schema) and the app's (`public`); plus `postgresOptions()` and `synchronizeSchema()` (`src/data-source.ts`)
- `packages/contracts` (`@repo/contracts`) — oRPC contract-first route definitions (`@orpc/contract` + zod 4): `src/base.ts` (shared errors, pagination/id params) and one folder per resource with `schemas.ts` (responses and POST/PATCH bodies), `params.ts` (GET queries, when there are any), `contracts.ts` (routes); implemented by the api, see `docs/contracts.md`. **Contracts only describe the api** (routes, params, bodies, responses): business logic goes in a framework-free package of its own
- `packages/events` (`@repo/events`) — queue message contracts: the JSON envelope (`id`, `type`, `version`, `occurredAt`, `data`), one zod schema per message type, and the RabbitMQ topology constants; its build also writes JSON Schema to `dist/schemas/` for non-Node workers
- `packages/storage` (`@repo/storage`) — provider-neutral object storage: the `ObjectStorage` abstract class (put/get/head/delete/deletePrefix, signed upload/download URLs), drivers (`gcs`: V4 signed URLs; runs against the `fake-gcs-server` emulator locally), and `createObjectStorage(options)` (no Nest code; the api provides `ObjectStorage` with its own factory provider in `StorageModule`); see `docs/storage.md`
- `packages/fixtures` (`@repo/fixtures`) — sample data in `src/data/`, loaded by `script/seed`; `@repo/fixtures/api` (`src/api/`) holds request/response cases per api endpoint, run by the api's endpoint specs and shared with the web tests (type-only dependency on `@repo/contracts`)
- `packages/config` (`@repo/config`) — validated env config (zod + `@t3-oss/env-core`): `@repo/config/shared`, `/api`, `/web`, `/worker`, `/e2e`
- `infra/` — OpenTofu for the GCP resources outside Railway: `modules/media-bucket` (private bucket, CORS, service account with object admin on it) and one root per environment (`envs/dev`; its values, the GCP project and web origin, in a gitignored `terraform.tfvars` copied from `terraform.tfvars.example`), state in a GCS bucket per environment named after the project; applied by hand, CI (`.github/workflows/infra.yml`) only runs `fmt`/`validate`; service account keys are made with `gcloud`, never in tofu; see `docs/infrastructure.md`
- `tsconfig.base.json` (root) — shared compiler options; every package's `tsconfig.json` extends it via `../../tsconfig.base.json` and adds its own framework options (Next.js in `apps/web`, decorators in `apps/api`, `apps/worker`, and `packages/entities`)

## Documentation

`docs/` holds the project documentation; `docs/README.md` is the index.

- **Before starting work, read `docs/README.md` and the pages relevant to the task** (e.g. `docs/database.md` before touching entities, `docs/testing.md` before writing tests).
- **Every feature has a story** in `docs/stories/` (`NNNN-slug.md`, see `docs/stories/README.md`): story, numbered acceptance criteria, status. A new feature starts with its story (`status: proposed`) landing on `main` in its own small `docs` PR, so its number is taken before work starts (check `gh pr list` and `git branch -a` for numbers already in use); mark it `done` and fill in its Implementation section when the feature is finished. Behaviour changes update the story too. **A story that changes the UI isn't done until its main flow has a browser test** in `apps/e2e`, named `S-NNNN ACn: …`.
- **Bigger or uncertain work has a plan** in `docs/plans/` (`NNNN-slug.md`, `P-NNNN`, see `docs/plans/README.md`): goal, options, proposal, open questions, and the stories it produces. Plans land on `main` in their own `docs` PR before work starts (pick the number the same way as a story's); their stories are written once a plan is `accepted`. **Once a plan's work is merged, retire the plan**: first move its lasting content to `docs/decisions/`, the docs pages, and its stories, and fix links to it; cut it down to a stub with `status: done`, so its number isn't reused. **Stories, plans, and decisions have no index tables** (they made parallel PRs conflict): the folders are the lists, and status lives in each file's frontmatter. Decisions are one file each, `docs/decisions/<title-slug>.md`.
- **Follow-ups are GitHub issues**: small cleanups or ideas that come up mid-task and aren't worth a plan or story yet go in `gh issue create --label <label>` (`bug`, `enhancement`, `chore`, `tests`, `infra`, `documentation`). Close them from the PR that does the work with `Fixes #N`.
- **Keep stories current.** When a requested change relates to an existing story, update that story in the same branch: adjust the acceptance criteria (add, reword, or remove; don't renumber the others, since tests and commits cite them), and the story text, notes, or title if the change goes further. **Before changing a story, show the user the proposed story changes and wait for confirmation**; don't edit a story's intent or criteria silently. If a change fits no story, propose a new one.
- **Keep the docs current.** When a change makes any page inaccurate (renamed file, new script, env var, behaviour change), update that page in the same commit. Add an entry to `docs/decisions/` for non-obvious choices and to `docs/troubleshooting.md` for confusing failures you solve. If this file and `docs/` disagree, fix whichever is wrong.

## Commands

Run from the repo root (pnpm 12, Node ^22.22.3 / ^24.15 / >=26). Day-to-day entry points are the `script/` files ("Scripts to Rule Them All" style). **`script/` holds only these entry points**: don't add one-off, debugging, or app-specific scripts there. Check a behaviour with a test (unit, integration, or browser); a CI-only helper goes in `.github/scripts/`.

```sh
script/bootstrap    # first-time setup: checks pnpm/Docker, runs script/update, creates .env/.env.test from the .example files and prompts for empty or missing values (generates BETTER_AUTH_SECRET if left empty)
script/seed         # starts the compose services and loads @repo/fixtures into the dev database via the api's seeder (idempotent)
script/server       # Postgres, RabbitMQ, Mailpit, fake-gcs (docker compose, detached) + api, web, and worker dev processes and package watch builds via Turbo; Ctrl-C stops everything including the containers. Mailpit: http://localhost:8025, RabbitMQ UI: http://localhost:15672
script/test         # every workspace's suites (unit + integration + browser), starting the compose services first; -a=api / -a=web / -a=worker / -a=e2e (repeatable) for just those apps and the packages they use
script/update       # updates every dependency to the newest version its package.json range allows (never widens a range; @repo/* excluded) and reinstalls
```

Underlying commands:

```sh
pnpm install
docker compose up -d --wait   # Postgres 17 (DB_* values from .env), RabbitMQ 4.3, Mailpit, fake-gcs; all have healthchecks
pnpm dev            # turbo run dev (all apps)
pnpm build          # turbo run build
pnpm lint           # oxlint --deny-warnings (whole repo, not per package)
pnpm check-types    # turbo run check-types
pnpm test           # turbo run test (unit tests only: api, worker, web, @repo/storage)
pnpm format         # oxfmt (format:check to verify)
```

Target a single workspace with a Turbo filter, e.g. `pnpm exec turbo dev --filter=web` or `pnpm exec turbo build --filter=api`. Alternatively `pnpm --filter <name> <script>`.

`apps/api` uses Vitest. Unit specs live next to source as `src/**/*.spec.ts`; integration specs (Supertest against the full `AppModule`) live in `test/**/*.integration.spec.ts` (grouped by feature, e.g. `test/auth/`), need the database running, and run serially. They use `.env.test` on top of `.env`, i.e. the `app_test` database, which the integration global setup (`test/global-setup.ts`) creates on the same Postgres server if missing; it refuses to run if `DB_NAME` doesn't end in `_test`:

```sh
pnpm --filter api test                              # unit tests
pnpm --filter api test:integration                  # integration tests
pnpm --filter api test:integration test/account/get-account.integration.spec.ts   # single file
pnpm --filter api test:integration -t "rejects invalid"                 # by test name
```

`apps/worker` is set up the same way (`pnpm --filter worker test` / `test:integration`). Its integration specs boot the full `WorkerModule` against real Postgres, RabbitMQ, and Mailpit: the global setup creates the test database and syncs its schema (the worker itself never does), and creates the RabbitMQ vhost from `RABBITMQ_URL` in `.env.test` (must end in `_test`) via the management API; tests read emails through Mailpit's HTTP API. See `docs/testing.md`.

`apps/web` has component tests in `test/**/*.spec.tsx` (and `.spec.ts`) (`pnpm --filter web test`): Vitest + jsdom + Testing Library, with every api call answered by MSW at the network boundary (`test/server.ts`); test what the user sees through accessible queries, not implementation. See `docs/testing.md#web`.

`apps/e2e` holds the Playwright browser tests (`tests/*.spec.ts`). Import `test`/`expect` from `fixtures.ts` (its `page` fails a test on console errors); create test data through `helpers/api.ts`. They need the api and worker built (`script/test -a=e2e` does that) and Chromium (`script/bootstrap` installs it):

```sh
pnpm --filter e2e test:e2e                          # whole suite (desktop + phone)
pnpm --filter e2e test:e2e -g "S-0001" --project=desktop   # one story, one viewport
pnpm --filter e2e exec playwright show-report       # report with traces of failures
```

## Architecture notes

- **Nothing identifying the deployment is committed.** `.railway/railway.ts` reads the Railway project name, the GitHub repo, and the bucket from `RAILWAY_PROJECT_NAME`, `RAILWAY_GITHUB_REPO` (default `GITHUB_REPOSITORY`), and `RAILWAY_GCS_BUCKET` (the release workflow passes repository Actions variables); `infra/` takes its values from each root's gitignored `terraform.tfvars`. Keep it that way: no project IDs, domains, or repo names in the repo.
- **This repo is a template**: `My App` (display name) and `app` (database, RabbitMQ, exchange, and bucket names) are placeholders a new project renames; the list is in `README.md` ("Starting a project from this template").
- **The app isn't live yet.** There are no real users; the only deployment is the Railway dev one, and its data is disposable. So don't spend effort preserving data or compatibility: no data-preserving migration SQL, backfills, state conversions, old-route aliases, or staged deploy orders. Make the change cleanly and reset instead (locally `docker compose down -v` and `script/seed`; on Railway dev, drop the affected tables or the database), listed in the PR's manual-steps issue. This changes once there are real users.

- Internal packages are linked with pnpm's `workspace:` protocol. `pnpm-workspace.yaml` also sets `engineStrict: true` (pnpm refuses to install on a Node version outside the root `engines`, which reflects the strictest dependency: the latest Nest CLI's `@angular-devkit/core`). pnpm 12 enforces `minimumReleaseAge` (24h) by default: versions published less than a day ago are rejected unless listed in `minimumReleaseAgeExclude` (pnpm adds entries there itself when a specifier can only be met by such a version; they can be removed once the version is a day old).
- Turbo tasks (`turbo.json`): `check-types` depends on `^check-types`, and `build`, `test`, `test:integration`, and `dev` depend on `^build`; `build` outputs `.next/**` and includes `.env*` in its cache inputs. `dev` is uncached and persistent. `apps/web/turbo.json` makes web's `check-types` also depend on web's `build`, because `next build` and `next typegen` both write `.next/types` and race when run in parallel.
- Web's `check-types` runs `next typegen && tsc --noEmit`, so route types are generated before type-checking.
- Linting is **oxlint** with one root `.oxlintrc.json` (no per-package lint tasks or ESLint). It enables the `correctness` (error) and `suspicious` (warn) categories plus the typescript/unicorn/oxc/import plugins; `overrides` add react/jsx-a11y/nextjs for `apps/web`, and vitest for api, worker, and package tests. `--deny-warnings` makes any warning fail. Formatting is **oxfmt** (`.oxfmtrc.json`, Prettier-compatible, `printWidth` 80); it formats CSS and JSON too and sorts `package.json` keys. Neither checks for undeclared Turbo env vars, so remember to add new env vars to `turbo.json` yourself.
- **Releases deploy from CI.** Pick the version with the rules in `docs/deployment.md#choosing-the-version` (any `feat` since the last release → MINOR, only `fix` → PATCH; every version ships as `-rc.N` prereleases first and is promoted to the plain tag once good). Pushing a `v*` tag runs `.github/workflows/release.yml`: `script/test -a=<app>` in parallel jobs for the apps affected since the last passing release (`.github/scripts/affected-apps`: Turbo's package graph, plus e2e whenever api/web/worker is affected, and everything when `.github/` or `script/` changed), then, if all pass, `railway up` for the api, worker, and web (a dev deployment on Railway; Railway doesn't deploy on pushes). A `config` job first runs `railway config apply` on `.railway/railway.ts` (Railway Infrastructure as Code: every service's build/pre-deploy/start commands and variables, secrets as `preserve()`), refusing destructive changes. **Change Railway settings in that file, not the dashboard** (the next release overwrites dashboard edits), and add an app's new env var to its service's `env` there too; see `docs/deployment.md`.
- TypeScript is strict with `noUncheckedIndexedAccess` enabled (from `tsconfig.base.json`).
- All packages are ESM (`"type": "module"`).
- **`apps/api` and `apps/worker` are native ESM (NestJS 12 is ESM-only).** Relative imports must include the `.js` extension (`import { AccountModule } from "./account/account.module.js"`), as must deep imports into packages without an `exports` map (e.g. `supertest/types.js`). `main.ts` uses top-level `await`.
- The whole repo uses **TypeScript 6**, held there by its `^6` range, which `script/update` never widens (don't run `pnpm update --latest`: pnpm 12 bumps TypeScript to 7 despite `updateConfig.ignoreDependencies` in `pnpm-workspace.yaml`): the Nest CLI (`nest build`/`start`) and schematics (`nest g`) need TypeScript's compiler API, which TypeScript 7.0 doesn't ship (expected back in 7.1). `apps/api`'s and `apps/worker`'s tsconfigs enable `experimentalDecorators` and `emitDecoratorMetadata` (needed for Nest's constructor injection). `nest build` uses `tsconfig.build.json` (excludes specs and `test/`) and outputs to `dist/`; `check-types` covers `src`, `test`, and the Vitest configs.
- Generate Nest resources with the CLI from `apps/api`, e.g. `pnpm exec nest g resource widgets`; generated code uses the Nest default single-quote style, so run `pnpm format` afterwards.
- **Env config lives in `@repo/config`; don't read `process.env` directly.** (In the web app's client code, build-time constants Next.js inlines, `NODE_ENV` and the service worker version, are read in `apps/web/lib/build.ts` only.) Add a variable to the zod schema in `packages/config/src/api.ts`, `web.ts`, or `worker.ts` (or `shared.ts` for all; `database.ts` holds the `DB_*` vars the api and worker share), add it to `.env.example` (and to `.env.test.example` only if tests need a different value), and import `env` from `@repo/config/api`, `/web`, or `/worker`. Validation runs at import time, so a missing or invalid value fails startup.
- `shared.ts` loads the **repo-root** `.env` into `process.env` when first imported, finding the root by walking up from `process.cwd()` to `pnpm-workspace.yaml` (not via `import.meta.url`, which breaks when Next.js bundles it; its `fs` calls carry `/*turbopackIgnore: true*/` so `next build` doesn't trace the whole repo). When `NODE_ENV=test` it loads `.env.test` first, which holds only test overrides (currently `DB_NAME`, `RABBITMQ_URL` with a `_test` vhost, and short `JOB_RETRY_DELAYS_MS`). A set variable is never overwritten, so precedence is shell/CI > `.env.test` > `.env`. It uses `node:fs`, so `@repo/config/web` is for `next.config.ts` and server code only, not client components (client-side vars would need `NEXT_PUBLIC_` and Next's own inlining). `.env` and `.env.test` are gitignored; the `.example` files are committed. docker compose reads the `DB_*` values from `.env` too.
- `@repo/config` is built like `@repo/entities` (see below). Env var names are also listed in `globalPassThroughEnv` (and `API_URL` in the web `build`/`dev` task `env`) in `turbo.json` so values set in the shell reach tasks under Turbo's strict env mode, and the root files every package reads (`.env*`, `tsconfig.base.json`, `docker-compose.yml`, root `package.json`, `pnpm-workspace.yaml`) are `globalDependencies` so editing them invalidates the cache and marks every package affected (which CI relies on; add a new such file there).

### Database and auth (`apps/api`)

- **`@repo/entities` is built** (so are `@repo/config`, `@repo/contracts`, `@repo/events`, `@repo/fixtures`, and `@repo/storage`), because the compiled api and worker import it at runtime. Its `exports` point `types` at `src/index.ts` (so type-checking needs no build) and `default` at `dist/index.js`. Turbo's `build`, `test`, and `dev` depend on `^build`, but after editing packages while running a single command outside Turbo, run `pnpm --filter "./packages/*" build`. Add new entities to the `entities` array in `src/entities.ts` (and export them from `src/index.ts`); `postgresOptions()` registers that array.
- The DataSource options come from `postgresOptions()` in `@repo/entities` (`src/data-source.ts`), used by `apps/api/src/database.ts` and `apps/worker/src/database.ts`. Only the api changes the schema: whenever `NODE_ENV !== "production"` it runs `synchronizeSchema()`, which creates every Postgres schema the entities use (`CREATE SCHEMA IF NOT EXISTS`, which TypeORM's `synchronize` doesn't do) and then synchronizes, under a Postgres advisory lock. **The worker never synchronizes**, so the api must have run after an entity change. There are no migrations yet; the first one will need to create the `auth` schema.
- `src/database.ts` exports `initializeDataSource()` (connect + schema sync) for standalone scripts. `src/seed.ts` (`pnpm --filter api seed`, i.e. `nest start --entryFile seed`; use `script/seed`) uses it with `createAuth` to run `src/fixtures/seed-fixtures.ts`, which signs fixture users up through Better Auth and marks them verified (app records it adds later are written with TypeORM). Fixture records reference each other by natural keys (e.g. email), type-checked via `as const`. The fixture users have a public password, so the seeder never runs on a deployed environment; reference data a deployment needs gets its own seed command, run as the api's Railway pre-deploy.
- Better Auth (`src/auth/auth.ts`) is mounted at `/api/auth` by `@thallesp/nestjs-better-auth`, configured through `AuthModule.forRootAsync` with the TypeORM `DataSource` and the api's `JobPublisher` (`src/messaging/`, publish only) injected. Google sign-in (`socialProviders.google`) is on only when `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are set (the web's button: `GOOGLE_SIGN_IN` in `@repo/config/web`); linking to an existing account by email is Better Auth's default (both sides verified). Email verification is required, all Better Auth defaults (`docs/auth.md#email-verification`): sign-up doesn't sign in, `sendVerificationEmail` publishes an `email.verify-email` job (not awaited) for the worker, and links are built from `BETTER_AUTH_URL`, the **web origin**. That module **registers a global auth guard**: every route requires a session unless decorated with `@AllowAnonymous()` / `@OptionalAuth()`. It also requires `bodyParser: false` in `NestFactory.create` (and in `createNestApplication` in integration tests).
- Better Auth talks to the database through the in-repo adapter `src/auth/typeorm-adapter.ts`. `createAuth` passes it an explicit map from Better Auth model keys (`user`, `session`, `account`, `verification`) to entities, so table and schema names are up to the entities. Entity **property** names must match Better Auth's field names (camelCase; map to snake_case columns with `@Column({ name })`). The Better Auth tables live in the **`auth` schema** under Better Auth's default names: `BaUser` → `auth.user`, `BaSession` → `auth.session`, `BaAccount` → `auth.account` (holds the password hash for email/password), `BaVerification` → `auth.verification`. `user` is a reserved word in Postgres, so hand-written SQL must quote it: `auth."user"`. A Better Auth plugin that adds models needs matching entities added to the adapter map; one that adds fields needs matching entity properties.

### Routes (`apps/api`, oRPC)

- Every app route is implemented from `@repo/contracts` with `@orpc/nest`: one Nest module per resource (e.g. `src/account/`), each with a controller and (once it has logic) a service. The controller has a single `@Implement(<resource>Contract)` method returning `{ <route>: implement(contract).<route>.handler(...) }`; `@Implement` registers the Nest routes and oRPC validates input/output and writes the response. `ORPCModule.forRoot(orpcConfig)` (`src/orpc.ts`, logs 500s) is in `AppModule`.
- `@AllowAnonymous()` covers every route its method implements, so public routes get their own `@Implement` method that `@Implement`s just that procedure.
- **Every `@Implement` method must take an unused `@Res() _res: unknown` parameter**, or Nest replies a second time after oRPC and throws `ERR_HTTP_HEADERS_SENT` on 204s.
- Get the user with `@Session() session: UserSession` (from `@thallesp/nestjs-better-auth`) on that method and pass `session.user.id` to the service. Services scope owned records to the owner (another user's record is `NOT_FOUND`), and throw `ORPCError` (from `@orpc/nest`) with codes from the base contract; map unique/FK violations to `CONFLICT`.
- Routes are at the api root (`/account`); web proxies `/api/*` to them. Integration test helpers: `test/helpers/app.ts` (`createApp`, which swaps the `JobPublisher` for the in-memory `publisher`; `signUp`, which opens the user's verification link from it; `signUpUnverified`, `uniqueEmail`, `deleteUsersAndClose`). Every route has one spec per endpoint (`test/account/get-account.integration.spec.ts`, …) whose successful requests come from cases in `@repo/fixtures/api`, which the web component tests share; add `test/helpers/builders.ts` (rows created through the api) with the first resource that needs them. **A new route gets its spec and cases the same way: follow the checklist in `docs/testing.md` ("Testing a new endpoint").**

### Object storage (`@repo/storage`)

- `StorageModule` (`apps/api/src/storage/`) provides `ObjectStorage` via `createObjectStorage` **only when `STORAGE_DRIVER` is set** (config: `STORAGE_DRIVER`, `GCS_BUCKET`, `GCS_API_ENDPOINT`, `GCS_PROJECT_ID`, `GCS_CREDENTIALS`), so the api runs without a bucket; a feature imports the module, injects `ObjectStorage` with `@Optional()`, and answers 503 without it. Put a record's files under one key prefix so deleting it can `deletePrefix`. See `docs/storage.md#in-the-api`.
- The `gcs` driver runs against the `fake-gcs` compose service (`GCS_API_ENDPOINT=http://localhost:4443`); in that mode it creates the bucket and signs URLs with a throwaway key. The emulator allows any origin (`-cors-headers` adds the signed size-range header), so browsers can upload to it. The api's integration tests use the `app-test` bucket (`.env.test`), the browser tests `app-e2e-test`. Tests: `packages/storage/test/gcs.integration.spec.ts`.

### Messaging and the worker (`apps/worker`)

- Jobs go through RabbitMQ (`docker compose` service `rabbitmq`) as plain JSON envelopes defined in `@repo/events`; no `@nestjs/microservices` transports, so non-Node workers can consume them. Producers (e.g. the api's `JobPublisher`) publish to the `app.jobs` topic exchange with the message `type` as routing key; the `email` quorum queue is bound to `email.#`. Full guide: `docs/messaging.md`.
- `src/messaging/`: `AmqpConnection` (one amqplib connection with built-in recovery; on every (re)connect it declares the topology and restarts consumers), `JobPublisher.publish(definition, createMessage(definition, data))`, and `JobConsumer`, which validates each message, dispatches it to the `JobHandler` for its `type` + `version`, acks on success, republishes failures to `<queue>.retry.<n>` (per-message TTL from `JOB_RETRY_DELAYS_MS`, `retry-count` header) and finally to `<queue>.parked`; invalid messages and `ParkJobError`s are parked at once. Register handlers with `amqp.addConsumer({ queue, handlers })` in a module's `onApplicationBootstrap` (see `src/email/email.module.ts`).
- Handlers must be idempotent (delivery is at least once). The verification email handler skips a job whose link has expired, and claims the message id (`EmailDeliveryService.sendOnce`) in `email_delivery` before sending and marks it sent after, so a redelivered message sends nothing.
- Email goes through the abstract `MailerService` (`src/mail/`; SMTP via nodemailer from `SMTP_URL`, tests override the provider). Templates are React Email components (`src/email/templates/*.tsx`, sharing `layout.tsx`; `renderEmail` gives the HTML and its plain-text part).
- Scheduled jobs would use `@nestjs/schedule` in the worker, with a Postgres advisory lock so only one worker runs each, and take the ids and "now" as parameters so their tests ignore other suites' data.
- The worker has no Better Auth instance and never writes `auth` tables; its integration tests insert users directly (test-fixture exception).

### Auth in `apps/web`

- The browser never calls the api directly: `apps/web/next.config.ts` rewrites `/api/auth/*` to `${API_URL}/api/auth/*` (default `http://localhost:3002`) and every other `/api/*` to `${API_URL}/*` (the oRPC routes; order matters, auth first), so Better Auth's session cookie is set on the web origin and no CORS is involved. `lib/auth-client.ts` creates the Better Auth React client with no `baseURL` for that reason.
- Better Auth rejects requests whose `Origin` isn't trusted, so the web origin must be in `trustedOrigins` in `apps/api/src/auth/auth.ts` (set from `WEB_URL`, default `http://localhost:3000`).
- `/login`, `/sign-up`, and `/check-inbox` (after sign-up: "we've sent a link", send it again) live in the `app/(auth)/` route group (centered shadcn card; redirects to `/dashboard` when signed in). Signed-in pages live in `app/(app)/`, whose layout calls `getSession()` (`lib/session.ts`, forwards the cookie to the api's `get-session`) and redirects to `/login`. The public `/verify-email` page (every verification link's `callbackURL`: forwards to `/dashboard`, or with `?error=` offers a new link) is outside both groups. Each `page.tsx` is a thin server component (for `metadata`) rendering a client component.

### Web UI (`apps/web`)

- Feature UI lives in `containers/<feature>/`; a resource typically gets a table container, `columns.tsx`, a form, a form dialog, and `queries.ts` for shared query options. App-wide pieces are in `components/` (`data-table.tsx`, `form-field.tsx`, `confirm-dialog.tsx`, `page-header.tsx`, `app-header.tsx` (its `links` are the nav), …); shadcn components are generated into `components/ui/` (`pnpm dlx shadcn@latest add <name>` from `apps/web`). `@/` aliases the `apps/web` root.
- Data: `lib/orpc.ts` exports `client` and `orpc` (TanStack Query utils) built from `@repo/contracts` with `OpenAPILink` at `${origin}/api` plus `ResponseValidationPlugin` (parses responses, turning `z.coerce.date()` fields back into `Date`s). Use `useQuery(orpc.x.list.queryOptions({ input }))`, `useMutation(orpc.x.create.mutationOptions())`, invalidate with `orpc.x.key()`. Browser-only.
- **TanStack Table is v9**: `useTable({ features: tableFeatures({...}), columns, data })`, `createColumnHelper<typeof features, Row>()`, `<table.FlexRender header|cell>`; register every feature/row model/sort or filter fn you use. Define columns in module-level `columns.tsx` functions (oxlint's `react/no-unstable-nested-components` rejects renderers defined in a component). Usage notes ship in `node_modules/@tanstack/react-table/skills/`.
- Forms use TanStack Form with the contract's zod schemas as validators (`validators: { onChange: createWidgetSchema }`) and `FormField` for label/errors; api errors show in the form, success toasts via sonner.
- **PWA:** `app/manifest.ts`, generated icons (`app/icon.tsx`, `app/apple-icon.tsx`, `app/icons/[icon]/route.tsx`, drawn by `lib/app-icon.tsx`; colours in `lib/brand.ts`), and a hand-written service worker `public/sw.js` registered by `components/service-worker.tsx` **in production builds only** (in dev it unregisters any leftover worker). Pages and `/api/*` always come from the network and are never cached (only the static `/offline` fallback is); hashed `/_next/static` assets are cache-first. Each build registers `/sw.js?v=<version>` (a random value per build from `next.config.ts`, read through `lib/build.ts`); the new worker takes over on the next launch and deletes older caches. Test it with `pnpm --filter web build && pnpm --filter web start` (see `docs/development.md#test-the-pwa-locally`). Keep pages that the worker may cache free of user data.
- **Phones:** signed-in pages and dialogs must fit 360 px without page scroll. `DataTable` wraps text below `sm`; hide minor columns with `columnClassNames` (`hidden sm:table-cell`) and fold key values into a visible cell with `sm:hidden`; dialogs containing a table need `grid-cols-[minmax(0,1fr)]` on `DialogContent`; a table whose hidden columns are sortable shows `SortMenu` on phones. The `components/ui/` controls are 44 px on touch screens (`pointer-coarse:` classes in the components, not global CSS).
- `apps/web/tsconfig.json` turns off `declaration`, which `tsconfig.base.json` enables; with it on, the destructured Better Auth client exports fail with TS2742.

## Working with the user

- **Keep the user on task.** If they switch to a new topic while the current task is unfinished, say so briefly (what's left, what's uncommitted) and offer to finish or park it before starting the new one. Small side requests can be done in between, but then bring the conversation back to the unfinished task.
- **Each task gets its own branch.** Before making changes for a new task, create a branch from an up-to-date `main` named after the task with a Conventional Commit type prefix, e.g. `feat/scan-targets`, `fix/login-form-mobile`, `docs/task-branches`; a story's branch starts with its ID, e.g. `feat/S-0001-scan-targets`. Don't start a task on `main` or on another task's branch. Ask before merging, pushing, or opening a PR.
- **Keep PRs small and scoped to one concern**: one package, one feature slice, or one refactor, with its tests and docs, that a reviewer can follow in one sitting and that passes the checks on its own. Renames, dependency bumps, refactors, and unrelated fixes get their own PRs rather than riding along. Infrastructure lands on its own and unwired: e.g. a PR adding a package like `@repo/storage` contains the package, its drivers, the local emulator, tests, and docs, and no app imports it; the first feature that needs it adds the wiring. A story or plan that touches several functional areas (e.g. contracts and api, worker, web) can be several PRs, stacked when one depends on another.
- **Commit at every task boundary, but ask first.** When a task is finished, and before moving on to a different one, propose a commit (what it would contain and the message) and wait for the user's go-ahead. Never commit without asking. Keep each commit to one task, so finish or set aside the current task's changes before starting the next.

## Conventions

- Always use [Conventional Commits](https://www.conventionalcommits.org/) for commit messages (enforced by commitlint in the lefthook `commit-msg` hook; `pre-commit` formats and re-stages staged files with oxfmt, then runs oxlint on them and type-checks every package, see `docs/development.md#git-hooks`): `<type>(<optional scope>): <description>`, e.g. `feat(web): add scan list page`, `fix(ui): correct button focus style`. Common types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`. Use a workspace name (`web`, `api`, `ui`, `entities`, …) as the scope when a change is limited to one. `feat` and `fix` commits must end with a `Story: S-NNNN` trailer (one per story) naming a file in `docs/stories/`; a custom rule in `commitlint.config.mjs` rejects them otherwise.
- **Keep packages to one concern, and be deliberate about their imports.** Each package's `README.md` says what it's for, who uses it, what it may depend on, and what doesn't belong in it; read it before changing the package, and update it when the package's intent changes (a new package ships with its README). A package depends only on what its job needs, and framework or app wiring stays in the app that uses it: e.g. `@repo/contracts` only describes the api, and shared business rules go in a package with no framework or database code. Before adding a dependency, an import from another package, or an export, check it fits the README; if it doesn't, put the code where it belongs instead.
- **Use TypeORM's query builder where possible**, rather than repository `find` options or raw SQL (`find` with a relation filter and `take` paginates with a second, `DISTINCT` query). Refer to entities, properties, and relations (`createQueryBuilder`, `innerJoin("widget.user", "user")`, `qb.subQuery()`, `andWhereExists`) so table and column names come from the entities. Write conditions as objects with find operators, not SQL strings, and check them with `satisfies FindOptionsWhere<Entity>`, since the builder's `where()` accepts any object: `.andWhere({ createdAt: MoreThanOrEqual(since), deletedAt: IsNull() } satisfies FindOptionsWhere<Widget>)`. Simple lookups by id or column (`findOneBy`, `existsBy`) can stay repository methods. Write a raw SQL string only when the builder can't express the query (e.g. Postgres functions like `pg_try_advisory_lock`), with a comment saying why.
- **Never cast in TypeScript**: no `as X`, `as unknown as X`, `<X>value`, or non-null assertions (`!`). Narrow instead: checks and type guards, parsing with the zod schemas, typing a variable at the boundary where a library returns `any`, or fixing the types upstream. If a cast is truly unavoidable, put a comment on it explaining why and what was tried instead. `as const` and `satisfies` aren't casts and are fine.
- **Never write to the Better Auth entities directly** (`BaUser`, `BaSession`, `BaAccount`, `BaVerification`, i.e. the `auth` schema): no repository `save`/`insert`/`update`/`delete`, query builder writes, or raw SQL against them. All changes must go through Better Auth (`auth.api.*`, the injected `AuthService`, or its HTTP endpoints) so its hashing, hooks, and session handling stay consistent. Reading them (e.g. to assert state in tests, or to join from app tables) is fine. The one exception is integration test fixtures: setup and teardown (e.g. deleting test users in `afterAll`) may write to them directly; the behaviour under test must still go through Better Auth.
